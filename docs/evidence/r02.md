## R02-B0 — isolated environment implementation (source level)

Scope: make the backend launchable inside a private Linux environment without
touching anything global. **No installation, no `dsh web`, no EXE run against a
real backend.** All results below are source-level and unit-level.

### What changed

- `src/main/core/isolation.ts` (new, pure): plan derivation from one validated
  root, strict charset validation, launcher-argument mapping, workspace rule
  (`~` + isolation → `<root>/workspace`; an explicit workspace always wins).
- `src/main/wsl/args.ts`: the start wrapper now exports `DSH_HOME`,
  `DSH_AGENTS_HOME`, `XDG_CACHE_HOME`, `TMPDIR`, `WSL_WEB_SHELL_ISOLATION_ROOT`
  **inside the distribution** (tilde expanded by Linux bash, never forwarded via
  `WSLENV`), and prefixes `PATH` with `<root>/runtime/bin` and the resolved node
  directory. New `PREPARE_ISOLATION_SCRIPT` (`mkdir -p` + `umask 077`, confined
  to the root) and `RESOLVE_RUNTIME_SCRIPT` (`dsh` + `node`, isolated runtime
  first, read-only).
- `src/main/wsl/gateway.ts`: `prepareIsolation()` and `resolveRuntime()` replacing
  the dsh-only resolver; an explicit `dshPath` still wins over detection.
- `src/main/core/supervisor.ts`: builds the plan, prepares the environment,
  resolves `dsh`/`node`, passes the validated root and workspace into the launch;
  preparation failure fails closed before any spawn.
- Config/settings: `isolateEnvironment` (default `true`) and `runtimeRoot`
  (default `~/.local/share/wsl-web-shell`), both validated, both requiring a
  backend restart; older settings files normalise to the isolated defaults.
- `tests/isolation.test.ts` (new, 28 tests): root/runtime validation, plan paths,
  workspace rule, exact launcher argv, `PATH` ordering, "no values in script
  text", preparation script confinement (no `rm`/`apt`/`npm`/`sudo`), runtime
  probe parsing, supervisor wiring, fail-closed paths, config validation.

### Defect found and fixed while testing the scripts

`sh -c SCRIPT a b` puts the first operand into `$0`, so the PID probe and the
signal helper — which both read `$1` while receiving a single argument — were
receiving nothing. Ownership verification would have failed closed on every real
launch (probe exit 10) and graceful shutdown would have silently signalled
nothing. Every single-argument script now runs with a fixed `$0` label
(`SCRIPT_ARGV0`) and reads its parameter from `$1`; a regression test executes
`PROBE_PROCESS_SCRIPT` against the test process itself and parses the result.

## R02-B0.1 — isolation root safety gate (source level)

Review finding from Issue #5: `isValidIsolationRoot` accepted `/` and `~`, so
`mkdir -p "$root"/{runtime/bin,…}` could target `/runtime` or `~/runtime`.

### Fixed

- **Root validation** (`src/main/core/isolation.ts`): structured parsing that
  rejects `/`, `~`, `~/`, `~/x`, `/srv`, `~user/...`, empty/repeated separators,
  `.`/`..` segments and shell-significant characters; a root must be a dedicated
  subtree at least two components deep, trailing slashes are normalised.
- **Linux-side enforcement**: the preparation and start wrappers repeat the rule
  set before writing, reject a root equal to `$HOME`, and fail with distinct exit
  codes (64 malformed, 66 unsafe root, 67 symlink/non-canonical, 70 creation
  failed).
- **Symlink traversal**: every component from home (or `/`) down to the root and
  each managed subdirectory is checked with `-L` *before* `mkdir -p`, then
  re-checked and canonicalised with `pwd -P`. A redirecting symlink fails closed
  without writing through it.
- **No destructive behaviour**: only `mkdir -p`; pre-existing files and modes are
  preserved (asserted by test).
- **Working directory**: `wsl.exe --cd` was replaced by an explicit `cd` inside
  the wrapper, so a tilde-prefixed workspace behaves identically regardless of the
  WSL build; missing/non-directory workspaces fail with a clear message, and
  `.`/`..`/empty workspace segments are rejected.
- **Docs**: isolation is documented as environment/prefix isolation, explicitly
  **not** an OS sandbox.

## M1 release candidate — close/termination diagnostics and pinned CI artifact

### Why diagnostics were added

The R02-B2 run left two unexplained observations: the window sometimes
disappeared without an app action, and one Electron instance ended without
`quit requested` in the log, without a Windows Error Reporting entry and without
a Crashpad report. Neither was reproducible. Instead of guessing, the app now
records the *cause* of every visibility change and every process end.

### What is recorded (cause only, never content)

| Signal | Meaning |
|---|---|
| `window main close-requested (visible=… focused=… quitting=no session-ending=no)` | a close request arrived from outside the app (X, Alt+F4, taskbar menu, page `window.close()`) |
| `window main hidden` / `shown` | actual visibility change, with the same flags |
| `window splash …` | the same for the always-on-top overlay, so a disappearing overlay is not mistaken for a disappearing window |
| `system session end announced` | Windows logoff/shutdown was announced before the close |
| `tray action: …` | any tray-initiated action (`open`, `status`, `restart`, `settings`, `quit`) |
| `uncaught exception: <name>: <message>` / `unhandled rejection: …` | a fatal main-process fault; the process still exits, but no longer silently |
| `child process gone (type=… reason=… exit=…)` | renderer/utility process failure |
| `app quit (exit code=…)` | the app reached Electron's quit event |
| `shutdown complete` | the orderly quit path finished; its absence identifies a run that was killed or crashed |
| `previous session: ended without a clean shutdown (last event: …)` | written on start-up when the previous run had no shutdown marker, quoting the last line it wrote |

Redaction: every recorded string passes `sanitizeForDisplay` (ANSI/control
stripping, token redaction) and `redactUserPaths` (`C:\Users\<user>`,
`/home/<user>`, `/mnt/<drive>/Users/<user>`, `/Users/<user>`). No page text,
cookie, environment value, backend payload or stack trace is stored; fatal errors
are logged as name + message only. Diagnostics never alter window behaviour and
their own failures are swallowed.

### Candidate causes and how each is now observable

| Candidate | Observable proof |
|---|---|
| user close (X, Alt+F4, taskbar "Close window"/thumbnail) | `close-requested` with `quitting=no session-ending=no` followed by `hidden` |
| page-initiated `window.close()` | identical signature — Chromium routes both through the same close request; it is distinguishable from the app's own quit (`quitting=yes`) but not from a user click |
| OS logoff/shutdown | `session-ending=yes` (or the `system session end announced` line) |
| app quit (tray, settings, second instance) | `quitting=yes`, `tray action: quit`, `quit requested`, `shutdown complete`, `app quit (exit code=…)` |
| renderer/utility crash | `child process gone (…)` / `renderer gone: …` |
| fatal JS error in the main process | `uncaught exception` / `unhandled rejection` line immediately before the exit |
| external kill (Task Manager, `Stop-Process`) | no shutdown marker; next start writes `previous session: ended without a clean shutdown`, quoting the last event |
| power loss / native browser crash | same as an external kill, plus no `app quit (exit code=…)` line |

The R02-B2 instance that ended silently had `tray action: open` as its last line,
which is consistent with an external termination (or a hard fault), but the run
predates this instrumentation, so the cause stays **unconfirmed**.
