### Why A14 blocks R02-B

`wsl-web-shell` is a supervisor, not an installer (spec rule 6: never silently
install DSH/Node). Without a `dsh` executable the launcher reaches exactly the
terminal `ERROR` state by design — that is already covered by unit and headless
smoke tests, and it is **not** an acceptance pass for the real WebUI path.

### Installation request (owner decision required)

Exact, minimal, reversible action proposed for authorization:

```
npm install -g @deepseek-ai/dsh@0.2.1-rc.5
```

- Target: npm prefix `<user>/.local` → binary `<user>/.local/bin/dsh` (already on
  PATH and already in the app's resolver list; nothing else is modified)
- Footprint: 686 packages added (dry-run resolution, nothing installed);
  disk cost measured precisely before the real install if requested
- Network: `registry.npmjs.org` over HTTPS only
- Rollback: `npm uninstall -g @deepseek-ai/dsh` (plus removal of the created
  `<user>/.dsh` if R02-B runs)
- Explicitly **not** included: no system packages, no Node upgrade (already
  v22.23.2), no changes to Windows assets, no `~/.agents` changes

Open questions to settle before R02-B, in the same authorization:

1. `DSH_HOME` isolation: the app spawns `wsl.exe` with an inherited environment
   and does not pass `DSH_HOME`/`DSH_AGENTS_HOME` into the distro. Either accept
   the default `~/.dsh` (absent today, so created fresh) or approve a small
   config addition (`dshHome`/`dshAgentsHome` passed as `env` before `exec`).
2. Provider credentials: first boot of the WebUI without a configured model
   provider is expected to render the original UI but not produce answers.
   Confirm UI-only acceptance is sufficient (no chargeable interactions).
3. Test workspace path under `<user>/...` for the isolated project, and confirm
   that no agent/exec commands will be run from the UI during acceptance.
