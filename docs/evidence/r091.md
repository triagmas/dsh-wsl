# R09.1 evidence — issue #11 (blank WebUI, DSH version)

Base: `c8f74c8` on `feat/r09-footer-bar` (PR #10, draft).

## 1. Blank WebUI area on Windows

### Symptom (owner acceptance, `c8f74c8`)

Backend healthy (`startup token exchange status=200`, `backend ready`), bar
rendered, and the whole WebUI area was one flat `rgb(11, 15, 22)` — the
app-owned page background. No `WebUI load failed`, no `renderer gone`.

### Cause

`READY` reaches `loadBackend()` **before** the window exists:

```
onStatusChange(READY) -> windows.loadBackend(origin)  // createBackendView()
                      -> windows.showMain()           // ensureMain()
```

`ensureBackendView()` created the `WebContentsView`, loaded the page into it and
then attached it with `this.mainWindow?.contentView.addChildView(view)`. On a
cold start (and after every restart, because the window is destroyed on
shutdown) `mainWindow` is still `null`, so the optional chain silently skipped
the attach. `ensureMain()` then called `ensureBackendView()` again, which
returned the existing view on its early-return path **without attaching it**.

Result: a loaded page in a surface that belongs to no window. The window shows
only its own `chrome` page, which is exactly the observed uniform
`rgb(11, 15, 22)`. Neither the log nor the DOM/cookie assertions could see it —
the window simply had no child views.

### Reproduction (before the fix)

`scripts/paint-probe.cjs --variant coldStart` composes in production order and
reads real screen pixels:

```
FAIL coldStart: capture=ok webuiPixel=[11,15,22] barPixel=[13,18,25] views=[]
composition smoke: FAIL a view created before its window is attached ... 0 children
```

`views=[]` is the defect: the window has zero child views while the WebUI page
is loaded.

### Fix

`src/main/electron/windows.ts`:

- `attachBackendView(view)` — attaches the view whenever a window exists and the
  view is not already a child; no-op while there is no window yet.
- `ensureBackendView()` calls it on **both** paths (existing view, new view).
- `ensureMain()` attaches an already existing view and calls `syncBackendView()`.
- `syncBackendView()` attaches a missing view, keeps the WebUI the top-most
  child (re-attach) and re-applies `computeViewBounds` — called from `show`,
  `ready-to-show`, the footer `did-finish-load` and display-metrics changes.
- `layoutMain()` logs the resolved geometry once per window
  (`webui layout: 1280x828 at 0,0 (content 1280x860)`); the acceptance log had no
  geometry at all, which is why this defect was not diagnosable from the log.

No remote content is injected, the bar stays 32 px at the bottom, the splash,
tray and settings popover are untouched.

### Verification

- `npm run composition:smoke` — 31 checks, including the new cold-start pair;
  negative-tested: reverting `windows.ts` makes both new checks fail.
- `npm run paint:probe` (xvfb, scale 1.0 / 1.5 / 2.0) — 5/5 variants paint the
  remote page: `coldStart`, `baseline`, `baseline2`, `reapply`, `sibling`.
- `npm run paint:probe` on the Windows CI job — real desktop pixels, see the
  run referenced in the PR comment.

## 2. Installed DSH version shown as `DSH —`

### Cause

`dsh --version` was probed with
`wsl.exe -d <distro> --exec <runtime>/bin/dsh --version`. `--exec` starts the
executable directly with the distribution's minimal PATH, and an npm-installed
`dsh` is a shell shim whose first line is `#!/usr/bin/env node`. The runtime
Node.js lives in `~/.local/bin`, which is not on that PATH, so the shim dies
with `env: 'node': No such file or directory` and exit code 127. The launcher
never had this problem because `START_WRAPPER_SCRIPT` prepends the resolved
runtime directories to `PATH`.

### Fix

`VERSION_PROBE_SCRIPT` (`src/main/wsl/args.ts`) is executed as
`wsl.exe -d <distro> --exec /bin/sh -c <script> <dsh> <node>`: it prepends
`dirname(node)` to `PATH` and then `exec`s the executable with `--version`.
`nodePath` is the same resolved runtime the backend starts with; when no runtime
was resolved the old direct `--exec <dsh> --version` form is kept. Both paths are
validated before use, and a failing probe now logs the exit code plus one stderr
line instead of a bare "did not report a version".

### Verification

- `tests/wsl-args.test.ts`: argument shape with/without a runtime, rejection of
  unsafe paths, and a real `#!/usr/bin/env node` shim test — the old invocation
  exits 127 with `env: 'node': No such file or directory`, the new script prints
  `0.2.1-rc.5` and `parseDshVersion` yields `0.2.1-rc.5`.
- `tests/footer.test.ts`: `describeInstalledLabel('0.2.1-rc.5')` →
  `DSH 0.2.1-rc.5`, `describeInstalledLabel(null)` → `DSH —`.
